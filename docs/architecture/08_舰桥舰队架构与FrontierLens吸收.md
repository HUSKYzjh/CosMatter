# CosMatter 舰桥舰队架构与 Frontier Lens 吸收说明

## 1. 架构目的

CosMatter 的舰队不是装饰性的多 Agent 角色扮演，而是将不同风险、权限和工件类型分配到不同的受控任务单元。原有的材料文献证据状态机仍然是科学结论的唯一放行路径；舰队层负责组织任务、路由工件、呈现运行状态，并为后续计算工作流预留边界。

系统采用四层组织：

```text
研究者 / 人工批准
        ↓
舰桥（跨舰队路由、工件契约、权限与门禁）
        ↓
舰队旗舰（本舰队唯一内部通信中继）
        ↓
功能舰（工具函数与子 Agent） → 太空梭（单一、小微、可回收任务）
```

功能舰之间不允许隐式点对点通信。一艘功能舰向旗舰发送“状态 + 工件引用”，旗舰完成权限、模式和审核状态检查后，才向下一艘功能舰发出“已批准任务包”。这个约束使消息可以审计，也避免多个模型彼此引用未核验的文本。

## 2. 十支舰队与职责边界

| 舰队 | 主要方向 | 向舰桥交接的核心工件 | 当前边界 |
|---|---|---|---|
| 开拓舰队 | 本地文献库、数据集、工作目录和语料冻结 | `corpus_manifest`、`dataset_registry` | 可用；只处理团队有权使用的本地来源 |
| 群星舰队 | 结构化数据库、分析脚本、关系候选 | `knowledge_graph_projection`、`analysis_run_record` | 关系只来自已审查事实，不把相关性说成因果 |
| 天体观测舰队 | 受控检索、筛选、授权解析和事实草案 | `candidate_screening`、`parse_receipts`、`source_maps` | 检索与解析均需批准；不在 UI 中保存全文 |
| 证据哨戒舰队 | 来源、单位、条件、反例边界和发布审计 | `accepted_evidence_cards`、`audit_summary` | 是进入科学结论和报告前的必经门禁 |
| 航路诊断舰队 | 冲突、条件分歧、缺失和返航补检 | `conflict_matrix`、`approved_return_plan` | 只提出需补检路线，不自行解释为规律 |
| 地平线探索舰队 | Research Gap 和可证伪验证路线 | `gap_candidates`、`validation_routes` | Gap 必须含证据、反证边界与人工复核 |
| 合成路线舰队 | 实验验证计划与表征记录模板 | `experiment_mission_plan` | 只生成待审核计划，不执行实验 |
| 量子远征舰队 | DFT 任务、输入清单、收敛与回执框架 | `dft_mission_plan` | **仅框架**，未接入 DFT 执行器 |
| 势场训练舰队 | DP 数据谱系、训练/验证计划、模型谱系 | `training_plan` | **仅框架**，未开始势函数训练 |
| 动力学巡航舰队 | MD 体系、协议、轨迹分析与稳定性框架 | `md_protocol` | **仅框架**，未接入 MD 引擎 |

三个计算舰队的“仅框架”状态在后端注册表和前端中均以紫色标识。它们不会被渲染成“正在计算”，也不会产生计算结果；只有在团队选择、配置和验证实际执行器后，才能把其状态改为就绪或运行中。

## 3. 旗舰、功能舰、工具与太空梭

每支舰队由一艘旗舰和 2–3 类功能舰组成。功能舰的“数量”是可配置的同型舰槽数量，不代表同时启动多个模型实例。旗舰的职责是：

1. 接收舰桥已经批准的任务包；
2. 将任务拆到本舰队允许的功能舰；
3. 校验工件名称、来源权限、审核状态和失败回执；
4. 收集子任务状态；
5. 只把注册过的工件交给舰桥。

工具函数和子 Agent 采用“设备/区域”命名，例如：

- **信标**：待办、优先级和人工门禁；
- **天体观察仪**：候选文献的元数据、主题和可比范围分析；
- **泊位管理员**：本地文献、数据集和工作目录登记；
- **采矿无人机**：在批准计划下周期性检查新增元数据，默认不联网；
- **暗物质分析仪**：从显式字段中寻找可解释的共现、缺失和分组；
- **来源定位器**：把人工复核的短片段锚定到页码、段落或表格；
- **反证探测器**：记录已执行的反例检索及结果边界；
- **训练铸造厂**：未来生成 DP 训练配置模板，不提交训练作业。

太空梭只执行一个短小、可回收的任务，例如单条 DOI 去重、一个字段质量检查、一条来源定位复查或一条 Gap 完整性核对。太空梭必须把结果返回所属功能舰，再经旗舰进入舰桥；它不拥有跨舰队权限。

## 4. 舰桥和舰队博物馆

**舰桥**是跨舰队协调层，而不是另一个自由生成的总控模型。它只接受带状态的类型化工件，例如 `source_maps`、`accepted_evidence_cards` 或 `conflict_matrix`，并根据预先登记的输入/输出契约决定是否允许交接。任一工件缺少来源、审核状态或权限记录时，舰桥应返回给原旗舰。

**舰队博物馆**是全局目录，登记所有舰队、舰船、工具/子 Agent、太空梭及其当前能力状态。它的两个作用是：

- 给研究者提供“系统里有哪些能力、是否真的接通”的可见清单；
- 让审计和方案撰写能将一个界面名称回查到工具 ID、输入、输出和边界。

博物馆中的“仅框架”项不属于系统已经实现的能力。

## 5. 新的三层可视化

原“任务规划”工作区被替换为舰桥通信页，按三层逐步下钻：

1. **派发任务**：显示十支舰队、当前由本地任务状态推导的运行状态、舰种数量、工具数量和任务方向。
2. **舰队通信**：点击舰队后显示旗舰、功能舰、显式双向通信账本和允许向舰桥交接的工件。所有路径均经过旗舰。
3. **舰载处理逻辑**：点击一艘舰后显示“批准任务包 → 工具/子 Agent → 返回旗舰审查”的处理链，以及所属太空梭的小微任务。

状态颜色具有固定语义：青绿为运行中，蓝色为就绪，琥珀色为等待批准，紫色为仅框架。状态由本地任务工件和注册表推导；没有真实运行记录时不会制造“实时任务”幻象。

页面提供 ZH/EN 切换。英文模式显示英文 UI；中文模式对产品名称 CosMatter、论文题名和作者名保留原文，其余本页界面文案使用中文。

## 6. Frontier Lens 的详细对照与吸收

Frontier Lens 的核心贡献不是“多 Agent”，而是把研究阅读组织为有边界的主题探索：问题限定、有限主题图、阅读路线、论文卡片/图谱、论文内部实体关系、证据回跳和中英界面。CosMatter 应吸收这种以结构化对象导航研究的交互思想，但不能复制其接口、数据模型、配置策略或将其阅读结果自动升级为材料科学结论。

| Frontier Lens 能力 | CosMatter 的吸收方式 | 不直接继承的部分 |
|---|---|---|
| 有界研究问题与主题图 | 开拓舰队冻结语料范围；天体观测舰队只执行批准检索；群星舰队投影本任务关系图 | 不以“未命中”宣称整个领域不存在工作 |
| Research Guide / Roadmap | 航路诊断舰队输出返航路线；舰桥显示任务交接和人工门禁 | 不让 LLM 在无 EvidenceCard 时自动生成科学导读 |
| 卡片式阅读顺序 | 文献图谱和论文阅读页保留候选、来源映射、阅读/复核入口 | 不加载、缓存或再分发受限全文 |
| 主题簇与论文内部关系 | 群星舰队用已审查事实、论文结构和关系工件生成可解释图谱 | 不将共现、引文或相似标题包装为材料因果关系 |
| Entity/Evidence 回跳原文 | 证据哨戒舰队的 EvidenceCard → source-map → 原文位置链路 | 未经人工审查的解析片段不能成为正式定位 |
| 相关论文与引文扩展 | 天体观察舰队的引文阵列在 DOI、来源和数量限制下扩展候选 | 不把开放元数据与全文证据混为一谈 |
| 可取消进度 | 保留状态机、回执、取消和失败状态；舰桥只显示真实本地投影 | 不把异步 HTTP 请求的“发起”误写成已经取消 |
| 双语界面 | 舰桥页面和全局语言状态提供 ZH/EN 切换 | 不翻译论文题名、作者、DOI 或提供方名称 |

后续可直接实现的吸收项是“阅读航线生成器”：它只能在已有候选、来源映射和审核状态上排序，并把排序理由写为可审计字段。不能采用“模型生成一条漂亮的阅读路线”来替代筛选依据或证据门禁。

## 7. 启用计算舰队前的最低条件

对 DFT、DP 势函数训练和 MD，至少应先确定：

1. 实际软件/执行器、版本、许可证、硬件与作业调度策略；
2. 输入数据授权、结构/标签来源、哈希和冻结版本；
3. 运行配置、失败重试、资源上限和停止条件；
4. 计算回执、模型/轨迹存储、输出摘要和可复跑脚本；
5. 由团队确认的数值验证标准与人工审查责任人。

在这些条件完成前，舰桥只能产生计划和清单，不得提交作业、声称完成计算或把模型输出写成材料结论。
